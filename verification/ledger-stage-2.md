## Group 1 - Out-of-order responses and uncertain outcomes (§ "Competing clients and uncertain outcomes")

| id | requirement (verbatim) | observable that proves it |
|---|---|---|
| S2-001 | "If search A starts before search B but finishes after it, the grid, table labels and booking form must describe B. A late response must not restore A's results." | Throttle search A (e.g. a proxy that delays its `/availability` response by 2s), run search B (different restaurant/date) immediately. After both settle, assert every `slot-{id}-{HH:MM}` present belongs to B's date and restaurant, `booking-summary` text names B's table label and B's local time, and no element anywhere carries A's date or table label. Assert on `availability-grid` innerHTML, not on a screenshot. |
| S2-002 | "If another client takes a table after the form opens, a `409 table_unavailable` response shows `booking-error` and refreshes availability. Preserve the selected form and its inputs so the diner can change their choice. Do not show a confirmation for that attempt." | Open the form for `slot-t_2-19:00` while signed in; in a second client `POST /reservations` the same table and slot; submit the form. Assert: `[data-testid="booking-error"]` present and nonempty; `[data-testid="confirmation"]` absent; `[data-testid="booking-form"]` still present with `booking-party-size` value unchanged; a subsequent `GET /availability` shows `t_2` no longer in that slot's `available_table_ids` (assert via the refreshed grid: `slot-t_2-19:00` has `data-available="false"`). |
| S2-003 | "If a booking response is lost, including after the booking commits, show nonempty `booking-uncertain` text, without `booking-error` or a new confirmation." | Drop the `POST /reservations` response at the proxy after the request reaches the server. Assert `[data-testid="booking-uncertain"]` present with nonempty trimmed text; `[data-testid="booking-error"]` absent; `[data-testid="confirmation"]` absent. The booking exists server-side - confirm with `GET /reservations/{reference}` via an authenticated second client. |
| S2-004 | "The unchanged form must retry with the same idempotency key and body. A successful retry removes the uncertainty/error elements and shows the original reference." | After S2-003, re-enable the proxy and click `booking-submit` without touching any field. Assert the retried request carried the same `Idempotency-Key` header value and a byte-identical body (record both at the proxy); assert `[data-testid="booking-uncertain"]` absent, `[data-testid="booking-error"]` absent, `[data-testid="confirmation-reference"]` text equals the reference the lost call created, not a second reference; assert `GET /reservations` shows exactly one reservation for that slot. |
| S2-005 | "A confirmed rejection uses `booking-error`." | Drop the response, then have a second client cancel or take the table so the retry receives a 4xx. Assert the retry shows `[data-testid="booking-error"]` with nonempty text and `[data-testid="booking-uncertain"]` absent and `[data-testid="confirmation"]` absent. Conflating uncertain with error fails this row. |
| S2-006 | "These rules apply to combination bookings too." | Repeat S2-002, S2-003 and S2-004 with `table_ids` of a declared pair (`slot-t_1+t_2-19:00`). Assert `booking-uncertain` on a dropped combined response, and that the successful retry returns the original combined `confirmation-reference`. |
| S2-007 | "The server remains authoritative; the browser must not manufacture a successful result from cached data." | After a successful booking, restart the container (state is in memory, so the booking is gone) and reload `/`. Assert the grid shows the slot available again and no `confirmation` element is present; the UI must not replay a cached confirmation. |
| S2-008 | "No background polling, live updates, cross-tab storage synchronization, or recovery across a page reload is required." | Not a failing row - it bounds the scope. Recorded so an implementation is not penalised for not building it. Judgment row: whether the absence of polling is visible as staleness a person would call a defect. Measure: leave a page open 60s after a second client books and confirm nothing changes on screen. |

## Group 3 - Combination testids, ordering and the API shape

| id | requirement (verbatim) | observable that proves it |
|---|---|---|
| S2-021 | "`slot-{t_a}+{t_b}-{HH:MM}` | A combination cell, e.g. `slot-t_1+t_2-19:00`. Ids in `combinable` order. Carries `data-available` like a single cell" | Fixture with `"combinable": [["t_2","t_1"]]` - deliberately not sorted. Search and assert the DOM contains `slot-t_2+t_1-19:00` and does NOT contain `slot-t_1+t_2-19:00`. Sorting the ids is the natural mistake and it fails every combination cell. | S2-023 | "`available_options` lists every single table and every declared pair with `capacity >= party_size` and no overlapping confirmed reservation on any member. Assert order, not set equality. |
| S2-024 | "`available_table_ids` stays exactly as it was — single tables only." | In the same response assert every `available_table_ids` entry is a declared single table id and that no pair id appears, and that the list matches the stage-1 definition for the same party size. |

| S2-026 | "**Pairs only** — never three or more. | S2-027 | "Combining is not transitive: `[t_1,t_2]` and `[t_2,t_3]` do not make `{t_1,t_3}` bookable." | Fixture with exactly that `combinable`. `POST /reservations` `table_ids: ["t_1","t_3"]` for a party size that only the sum of all three would satisfy → 422 `combination_not_allowed`. | S2-028 | "`table_id` is still accepted and means a set of one. Sending both is 422 `validation_failed`." | `POST /reservations` with `table_id: "t_1"` only → 201. With both `table_id` and `table_ids` → 422 `validation_failed`. Assert the code. |
| S2-029 | "Responses always carry `table_ids`. They also carry `table_id` **when the set has exactly one member**, and omit it otherwise." | Single booking: assert response has `table_ids: ["t_1"]` and `table_id: "t_1"`. Pair booking: assert response has `table_ids: ["t_1","t_2"]` and `"table_id" in body === false`. Assert the same on the `GET /reservations/{reference}`, `GET /reservations` list entries and the `PATCH` response, not only on create. |
| S2-030 | "Duplicate table id in the set | 422 `validation_failed`" | `POST /reservations` `table_ids: ["t_1","t_1"]` → 422 `validation_failed`. |
| S2-031 | "The pair is not in `combinable` | 422 `combination_not_allowed`" | Two large tables, no `combinable` entry → 422 `combination_not_allowed`. |
| S2-032 | "More than two tables | 422 `combination_not_allowed`" | Four tables declared combinable pairwise, `table_ids` of four → 422 `combination_not_allowed`. |
| S2-033 | "Any table in the set is taken for an overlapping interval | 409 `table_unavailable`" | Confirm a booking on `t_1` alone; then `POST /reservations` `table_ids: ["t_1","t_2"]` at an overlapping slot → 409 `table_unavailable`. | S2-034 | "`party_size` exceeds the combination's summed capacity | 422 `party_exceeds_capacity`" | Pair capacity 6, `party_size: 7` → 422 `party_exceeds_capacity`. Assert the code, and that it is not `combination_not_allowed` or `validation_failed`. |

| S2-038 | "The existing browser recovery and original-receipt requirements also apply to combined-table bookings." | Repeat S2-003 and S2-004 with `table_ids`. Assert the successful retry returns the original combined `confirmation-reference` and that the pair is occupied once, not twice. |

## Ambiguities in the stage-2 text, surfaced rather than resolved

| id | ambiguity | why it matters |
|---|---|---|
| S2-A1 | "Ids in `combinable` order" for `slot-{t_a}+{t_b}-{HH:MM}` — the specification never says what `available_options` does when a pair's two members are both individually available. It lists singles first and pairs after, so a pair that duplicates two singles is still listed. I read it as: both singles and the pair appear. If the implementation is meant to suppress a pair when its singles are free, `available_options` differs and S2-023 fails. Needs a ruling before code is written. |
| S2-A2 | "A confirmed rejection uses `booking-error`" — the text does not say whether the lost-response uncertainty element must be removed when the retry is rejected, or may remain alongside `booking-error`. I read it as removed (the outcome is now known). If it may remain, S2-005's second assertion is wrong. |
| S2-A3 | "`no-slots` ... Shown instead of the grid when the day has no slots" — "no slots" is not defined: is a day with opening hours but every slot fully booked "no slots", or does the grid still render with all cells `data-available="false"`? I read it as the day having no slot objects at all, so a fully-booked day still renders a grid. S2-018 depends on this. |
| S2-A4 | "Booking requires a signed-in user: clicking an available cell while signed out shows `auth-error` or navigates to `/login`, your choice." — `auth-error` is defined on the signup/login screens. Whether it may appear on `/` is not stated. I read it as permitted anywhere; if a grader only checks `/login`, an implementation showing it on `/` still passes. |
| S2-A5 | "at conventional desktop widths" is not a number. I have used 1280 CSS px. If the grader uses 1440 or 1024, S2-041 and S2-046 should be repeated there. |
| S2-A6 | "Available, unavailable, selected, loading, successful, refused and uncertain states must be visually distinct" — distinct from each other in how many properties is not stated. I have asserted distinctness on background, colour and border taken together, which is the weakest reading that still catches two states rendered identically. |
