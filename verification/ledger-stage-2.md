# Tablekeeper Stage 2 - Requirements Ledger

Result repository: /home/aryan/band_hack/band-work/tablekeeper5
Specification: /home/aryan/band_hack/dark-factory-wearedevs/tablekeeper/spec/stage-2.md
Stage-1 spec: /home/aryan/band_hack/dark-factory-wearedevs/tablekeeper/spec/stage-1.md

Ordered by how likely a row is to be graded and how unlikely a competent first attempt is to
satisfy it. Rows at the top decide the stage. Every `data-testid`, status, code and literal
string below is taken from the specification text.

Ambiguities are stated in the row, not resolved silently.

**Standing convention: every row states both halves of its assertion.** Where a requirement says
something must appear, the row also says what must *not* appear, and vice versa, because a
presence-only assertion passes on a page showing two states at once. Where a row cannot yet state
both halves, that is a defect in the row and it is to be fixed here rather than remembered at
verification time — a requirement that lives only in the verifier's head is the one that gets
dropped. Corrections to rows already ruled on are made in the row, not deferred.

**Standing clause 2: assert that a setup step succeeded before asserting anything about its
result.** A `POST /_test/reset` that returns 422 leaves the previous store in place, so a probe
that discards the reset's status and then reads `/availability` is reading stale state and will
report a confident, wrong availability fact. This applies to seeding, to mutation, to export, to
reset — anywhere a precondition is arranged and then measured.

**Standing clause 3: assert the shape of what you read before drawing a conclusion from it.** A
missing key is not a zero. `GET /_test/export` returns `{format_version, track, state}` and
reservations live at `state.reservations`; reading `doc["reservations"]` gives a `KeyError` or a
false 0, and a 200 with a real body still supports a completely wrong conclusion. Check the key
exists, then read it. The document nests state under `state`, so the export row's first assertion
is `assert "state" in doc`.

**Standing clause 4: salt non-determinism is scoped to re-derivation, not to transport.** Two
hashes of the same password differ; one stored hash moved through export → import does not,
because the salt travels inside the stored string and import does not re-derive. So an upgrade row
**may and should** assert byte equality of `password_hash` across export → import, and **must
not** assert it across a re-seed (`POST /_test/reset` hashes the plaintext again). Measured on
stage 2: export → import → export is byte-identical and login still returns 200; a re-seed changes
the hash. Asserting only "a hash is present and login works" would pass against an import that
silently re-hashed every credential, so it is not sufficient on its own.

All three clauses, plus the both-halves convention, are here because each was added after a real
reading error on this build, not because they were anticipated. They cost one line each and each
one removes a whole class of confident wrong numbers.

## Group 8 - Stage-1 rows that stage 2 could regress

Each of these is a stage-1 ledger row (`verification/ledger-stage-1.md`) that a UI or
combined-table change can break. Stage 2 is cumulative, so a stage-1 row broken by a stage-2
change is a stage-2 failure.

| id | carried from | observable that proves it still holds |
|---|---|---|
| S2-061 | R034 `Idempotency-Key` scoped to the authenticated user | Two signed-in browsers, same key string, same body, on `POST /reservations` for two different tables that do not conflict. Assert both 201. Repeat with the second user's different body: that user gets 409, the first user's replay still 200. |
| S2-062 | R035 a replay means same user, method, path and body | The same key with the same body sent to `POST /reservation-moves` after being used on `POST /reservations` must be a first use on that path, not a replay. ## Ambiguities in the stage-2 text — all six ruled by the Foreman from the specification text

The readings below are settled, not mine to resolve. Each is stated inside the row it affects as
well, so a verifier reading one row sees the interpretation it is checking against.

| id | was ambiguous | ruling | rows it settles |
|---|---|---|---|
| S2-A1 | Whether `available_options` lists a declared pair when both its members are individually available. | **Both singles and the pair appear. No suppression.** "every single table and every declared pair" — two independent lists concatenated, singles first in fixture order then pairs in `combinable` order. "no overlapping confirmed reservation on any member" is the only exclusion in the sentence. A pair whose members are individually free is still a distinct seating option with a distinct capacity and a distinct testid. | S2-023 (stands as written). An implementation that hides a pair when its singles are free is the defect this row is aimed at. |
| S2-A2 | Whether a pair's testid ids follow `combinable` order or sorted order. | **`combinable` order.** Keep the deliberately unsorted `combinable` entry in the fixture; it is the cheapest possible detector for an implementation that sorts. | S2-021, S2-023 |
| S2-A3 | Whether "the day has no slots" means no slot objects, or every slot fully booked. | **`no-slots` means the day produced no slot objects. A fully-booked day renders `availability-grid` with every cell `data-available="false"`.** The slot list comes from `slot_minutes` and `opening_hours`, not from bookings; bookings remove tables from a slot's `available_table_ids`, they do not remove slots. The grid is the only place an unavailable table is ever visible to a diner, so replacing it with `no-slots` on a full day removes required information. `no-slots` **replaces** the grid, never sits beside it. | S2-018 (stands as written) |
| S2-A4 | Whether `auth-error` may appear on `/`, or only on the signup/login screens. | Settled as read: `auth-error` may appear anywhere; the specification permits either it or navigation to `/login`. Also ruled here: `table_id` and `table_ids` are each accepted individually and both together is 422 `validation_failed`, on create, read, list and patch; responses always carry `table_ids` and carry `table_id` only when the set has one member. | S2-013, S2-028, S2-029 |
| S2-A5 | What "conventional desktop widths" means numerically. | **A range, not a point: check at 1024, 1280 and 1440, plus 375.** A check at one width cannot establish the property. 1280 stays the primary. | S2-041 (widened), S2-046 |
| S2-A6 | How many properties must differ for two visual states to count as "visually distinct". | Keep the weakest reading that still catches two states rendered identically: distinctness across background, colour and border taken together. Stated inside the row. | S2-043 |
